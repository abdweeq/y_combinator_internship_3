3. Three product ideas to test

Expected impacts below are hypotheses, not measured outcomes or guaranteed forecasts.

1 · Opt-in reminders for idle cards

Evidence: 35 backlog cards have no status transitions and were already at least 14 days old at the last recorded card event.

Hypothesis
Some unfinished work is forgotten. A useful, infrequent reminder could bring users back to review a card and choose a next step.
Expected impact
More return visits and more active days among users who subscribe to reminders. Test the daily active rate and seven-day return rate against a randomized control group; monitor unsubscribes.
Feature
Let users follow a card and opt into a digest when followed cards have not moved for 14 days. Include a direct link and simple snooze and unsubscribe controls. Treat reminders as suggestions: an idle card is not necessarily blocked.

2 · A personal “Next actions” view

Evidence: 102 cards remain unfinished in the snapshot: 44 in backlog and 58 in progress.

Hypothesis
A large shared board makes it harder to decide what to do next. A small personal queue could make the product useful as a daily starting point.
Expected impact
More repeated use on working days and shorter time to the first useful action. Compare active days per user and the seven-day return rate in an A/B test, while checking task completion time.
Feature
Allow users to pin a few cards, add a next-action note and optionally set a due date. Show those cards in a compact view with direct access to the board.

3 · Completion subscriptions and a progress feed

Evidence: 103 transitions enter complete, involving 101 distinct cards. The history also contains 16 backward transitions, so work can be reopened.

Hypothesis
People who monitor work may miss relevant updates. A concise feed could give them a useful reason to return and review progress.
Expected impact
More return visits by followers after relevant updates. Measure incremental return activity in an A/B test; check whether a digest replaces visits instead and monitor notification opt-outs.
Feature
Let users subscribe to selected cards. Offer an in-app feed and an optional digest of completed or reopened work, with links to the changed cards and a short history of what happened.

4. Definitions, limits and reproducibility

  • DAU definition: distinct user_id values in login_history per UTC date. This measures recorded logins; it cannot detect an active user whose session carries over without a new login.
  • Calendar coverage: 364 dates, including 9 dates with no recorded logins. Zero filling assumes continuous data collection; the dataset has no outage metadata.
  • Release boundary: 2 June 2018 is treated as the first post-release UTC day because no exact launch time or timezone is supplied.
  • Card activity: count an event only when both statuses exist and differ. Include cards with zero transitions. A creation is not a transition.
  • Interpretation: the supplied history spans months, despite the scenario's “one week” wording. No user-to-card ownership link, feature exposure, or support-ticket dataset is supplied. These records cannot establish why usage changed or attribute a card event to an individual user.
  • Next measurement step: add user-linked feature and card-action events, capture feature exposure, and test the ideas with randomized groups of eligible users.

To rerun the SQL, put answer.sql and analyze.cjs beside the repository's shiptivity.db and run node analyze.cjs with Node.js 24. The database is opened read-only; results are written to analysis-results.json.

-- Shiptivitas, Task 3: Analytics
-- Source: insidesherpa/-shiptivitas-3, shiptivity.db.
-- Kanban release date: 2018-06-02 (README).
-- Timestamps are Unix seconds; all calendar days below are UTC.
-- DAU is a login-based proxy: one user is counted once per day.
-- Calendar gaps are treated as zero activity within the observed date range.
-- These SELECT queries do not change the source database.

-- QUERY: daily_active_users
-- PART 1: Daily unique users and the mean before/after release.
WITH RECURSIVE
bounds AS (
    SELECT
        DATE(MIN(login_timestamp), 'unixepoch') AS first_day,
        DATE(MAX(login_timestamp), 'unixepoch') AS last_day
    FROM login_history
),
calendar(day) AS (
    SELECT first_day FROM bounds
    UNION ALL
    SELECT DATE(day, '+1 day')
    FROM calendar
    WHERE day < (SELECT last_day FROM bounds)
),
daily_logins AS (
    SELECT
        DATE(login_timestamp, 'unixepoch') AS day,
        COUNT(DISTINCT user_id) AS dau
    FROM login_history
    GROUP BY DATE(login_timestamp, 'unixepoch')
),
daily AS (
    SELECT
        calendar.day,
        CASE
            WHEN calendar.day < '2018-06-02' THEN 'Before release'
            ELSE 'After release'
        END AS period,
        COALESCE(daily_logins.dau, 0) AS dau
    FROM calendar
    LEFT JOIN daily_logins ON daily_logins.day = calendar.day
)
SELECT
    day,
    period,
    dau,
    ROUND(AVG(dau) OVER (PARTITION BY period), 4) AS period_average_dau,
    ROUND(
        AVG(dau) OVER (
            ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
        ), 4
    ) AS trailing_7_day_average
FROM daily
ORDER BY day;

-- QUERY: status_changes_by_card
-- PART 2: Include all cards, even cards with zero status changes.
-- Creation (oldStatus IS NULL) is not a status transition.
-- A priority-only edit is not a status transition either.
SELECT
    c.id AS card_id,
    c.name AS card_name,
    c.status AS current_status,
    COUNT(h.id) AS status_changes
FROM card AS c
LEFT JOIN card_change_history AS h
    ON h.cardID = c.id
    AND h.oldStatus IS NOT NULL
    AND h.newStatus IS NOT NULL
    AND h.oldStatus <> h.newStatus
GROUP BY c.id, c.name, c.status
ORDER BY status_changes DESC, c.id;

-- QUERY: matched_28_day_comparison
-- SUPPLEMENT: Equal-length, equal-weekday-composition windows.
-- Before: May 5--June 1. After: June 2--June 29. All dates inclusive.
WITH RECURSIVE
periods(period, start_day, end_day) AS (
    VALUES
        ('Before release', '2018-05-05', '2018-06-01'),
        ('After release', '2018-06-02', '2018-06-29')
),
calendar(day) AS (
    SELECT MIN(start_day) FROM periods
    UNION ALL
    SELECT DATE(day, '+1 day')
    FROM calendar
    WHERE day < (SELECT MAX(end_day) FROM periods)
),
daily_logins AS (
    SELECT
        DATE(login_timestamp, 'unixepoch') AS day,
        COUNT(DISTINCT user_id) AS dau
    FROM login_history
    GROUP BY DATE(login_timestamp, 'unixepoch')
)
SELECT
    p.period,
    p.start_day,
    p.end_day,
    COUNT(*) AS calendar_days,
    SUM(COALESCE(l.dau, 0)) AS active_user_days,
    ROUND(AVG(COALESCE(l.dau, 0)), 4) AS average_dau,
    (
        SELECT COUNT(DISTINCT user_id)
        FROM login_history
        WHERE DATE(login_timestamp, 'unixepoch')
            BETWEEN p.start_day AND p.end_day
    ) AS unique_users_in_window
FROM periods AS p
JOIN calendar AS c ON c.day BETWEEN p.start_day AND p.end_day
LEFT JOIN daily_logins AS l ON l.day = c.day
GROUP BY p.period, p.start_day, p.end_day
ORDER BY p.start_day;

-- QUERY: daily_status_changes_by_card
-- SUPPLEMENT: Daily activity per card, as requested in the task background.
-- Missing day/card combinations mean zero observed transitions.
SELECT
    DATE(timestamp, 'unixepoch') AS day,
    cardID AS card_id,
    COUNT(*) AS status_changes
FROM card_change_history
WHERE oldStatus IS NOT NULL
    AND newStatus IS NOT NULL
    AND oldStatus <> newStatus
GROUP BY DATE(timestamp, 'unixepoch'), cardID
ORDER BY day, cardID;

-- QUERY: transition_counts
-- SUPPLEMENT: Which directions did the cards move?
SELECT
    oldStatus AS from_status,
    newStatus AS to_status,
    COUNT(*) AS status_changes,
    COUNT(DISTINCT cardID) AS distinct_cards
FROM card_change_history
WHERE oldStatus IS NOT NULL
    AND newStatus IS NOT NULL
    AND oldStatus <> newStatus
GROUP BY oldStatus, newStatus
ORDER BY status_changes DESC, from_status, to_status;

-- QUERY: card_activity_summary
-- SUPPLEMENT: Evidence for product hypotheses.
-- Card age is measured at the latest card-history timestamp in the dataset,
-- not at the date on which this assignment is being completed.
WITH history AS (
    SELECT
        cardID,
        MIN(CASE WHEN oldStatus IS NULL THEN timestamp END) AS created_at,
        SUM(
            CASE
                WHEN oldStatus IS NOT NULL
                    AND newStatus IS NOT NULL
                    AND oldStatus <> newStatus
                THEN 1
                ELSE 0
            END
        ) AS status_changes
    FROM card_change_history
    GROUP BY cardID
),
cards AS (
    SELECT
        c.id,
        c.status,
        h.created_at,
        COALESCE(h.status_changes, 0) AS status_changes
    FROM card AS c
    LEFT JOIN history AS h ON h.cardID = c.id
)
SELECT
    COUNT(*) AS total_cards,
    SUM(status_changes) AS total_status_changes,
    SUM(status_changes = 0) AS cards_without_status_changes,
    SUM(status_changes <= 1) AS cards_with_at_most_one_status_change,
    SUM(status = 'backlog') AS backlog_cards,
    SUM(status = 'in-progress') AS in_progress_cards,
    SUM(status = 'complete') AS complete_cards,
    SUM(
        status = 'backlog'
        AND status_changes = 0
        AND created_at <= (
            SELECT MAX(timestamp) - 14 * 86400
            FROM card_change_history
        )
    ) AS unmoved_backlog_cards_at_least_14_days_old
FROM cards;
